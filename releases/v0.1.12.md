This release lets an Orca bot be the Front agent, pins Pi workers to a model per role, and fixes the heartbeat for a Controller running in pi.

The terminal Front agent stays the default. A config without `hosts.frontAgent.kind` works exactly as before.

**New**
- **An Orca bot as the Front agent (`hosts.frontAgent.kind: "orca-bot"`, `hosts.frontAgent.bot`)** (#50, #51):
  - **Waking the bot:** `start` does not schedule `statuswatch.mjs` for a bot. It creates one Orca automation for the bot instead. Every 5 minutes its precheck (`botwatch.mjs`) reads the Controller's `status.md` and wakes the bot only when one of these happens:
    - "Needs <human>", "Needs front agent" or "Problems" changed;
    - `status.md` is older than `hosts.frontAgent.staleMinutes` (default 25) or missing;
    - the Controller's host cannot be reached.

    A quiet project costs no model time. The bot reads `wake.md`, which says what changed, and follows `~/front-agent/<project>/FRONT_BOT.md`. That file holds the Front agent's rules written for a bot.
  - **Questions:** the bot puts open questions on "needs you" items and always also writes them as plain text in its chat.
  - **Code:** a bot writes no product code itself; code work goes through workers.
- **One bot for several projects:** projects that name the same bot share one automation and one precheck. The precheck keeps one state line per project, and a second `start` creates no duplicate.
- **Controller events to the bot (`CONTROLLER.md`):** with a bot on the same machine, the Controller also sends each front event with `orca orchestration send --to "bot:<name>"`. It uses `--type question` for new questions and blocks, `--type status` for everything else. `front-events.log` and `inbox.md` stay the record.
- **`status --json` and `doctor` with a bot:** they check that the bot exists (`orca bot list`) and that its watch automation exists (`orca automations list`), instead of the terminal's status watch.
- **Read access for the Controller (all Front agent kinds):** when `start` sets up a local Controller, it lets it read the project and its worker workspaces, but only for tools it finds installed:
  - lean-ctx: `allow_paths` in `~/.lean-ctx/config.toml`;
  - pi's context-mode: `Read(<path>/**)` in `<controllerDir>/.claude/settings.local.json`.

  A missing tool is skipped, and a grant that cannot be written never fails `start`.
- **Pi workers pinned per role (`agents.piRoleModels`)** (#49): `{ "Developer": "provider/model-id" }` starts a Pi worker of that role on that provider and model instead of its tier's model. Other roles and agents keep their tier, and an explicit `--model` still wins. A pinned role is not moved by `--tier` or the escalation ladder.

**Fixed**
- **Heartbeat, `start` and `status` find a Controller terminal that pi renamed** (#49): pi titles its terminal `π - <cwd>`, so the Controller was never woken. A pi-style title whose folder is this Controller's directory now counts; the exact `<project> · Controller` title is still preferred.
- **A status watch left over after switching to a bot stays silent:** it no longer sends text into a terminal. `start` removes the launchd job, and `statuswatch.mjs` exits at once under cron.

**Documented**
- `docs/orca.md` has two new sections, "Front agent as an Orca bot" and "Read access for the Controller".
- `docs/roles.md`, `docs/workflow.md` and `docs/de/workflow.md` name the bot as a Front agent kind.
- `docs/capacity.md` covers role pinning.
- The example model name is now the neutral `provider/model-id`.

**Switching to a bot Front agent**
1. Create the bot in Orca on the machine where you work. `start` cannot create it, because Orca only creates a bot once you accept it.
2. Give the bot's `SOUL.md` this line: "For each agentic-factory project, follow ~/front-agent/<project>/FRONT_BOT.md".
3. In the project's `factory.config.json`, set `hosts.frontAgent.kind` to `"orca-bot"` and `hosts.frontAgent.bot` to the bot's name as `orca bot list` shows it. Optionally set `hosts.frontAgent.staleMinutes`.
4. Run `agentic-factory update`, then `agentic-factory start`. Then check with `agentic-factory doctor`.

For a second project with the same bot, repeat steps 3 and 4.

**Limits**
- Nothing has run against a real bot yet. The automation, the precheck as Orca runs it, and the `bot:` messages were tested against a fake Orca only. The command for adding a new item is not confirmed, so `FRONT_BOT.md` tells the bot to check `orca bot item --help` (F51).
- A Controller on another host cannot send to the bot, because `bot:` only reaches bots on the same machine. The bot watches that Controller's `status.md` over ssh every 5 minutes.
- The read grants cover a local Controller only. Add them by hand on a remote Controller host (F52).
- A lasting problem (a stale or missing status, an unreachable host) wakes the bot once, when it starts, not every 5 minutes.

After updating, run `agentic-factory update` in each project.

Known gaps: #38 (`update --help` runs the update), #39 (`start` on the Controller's own host), F49, F50, F51, F52.
