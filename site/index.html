DevOps-Harness für Software, die Agenten bauen

Ein Mensch.Ein Gesprächspartner.Eine Fabrik, die nachts weiterbaut.

Agentic Factory ist die Arbeitsweise und das Werkzeug, mit dem ein Mensch viele KI-Agenten Software bauen lässt, ohne den Überblick zu verlieren: ein Front-Agent, der zuhört, ein Controller, der unbeaufsichtigt steuert, unabhängige Prüfer, gemessene Kapazität und eine Pipeline, die sich selbst verbessert.

Auf einen Blick

Wie es funktioniert

Der Mensch spricht mit genau einem Agenten. Alles andere passiert dahinter: auf dem eigenen Rechner, auf einem oder mehreren Servern, oder beides.

1Ansprechpartner für den Menschen
0Pushes nach main ohne bestandenes Review. Git lehnt sie ab.
2Review-Runden, dann wird integriert. Der Rest wird Schuld mit Kategorie.
24/7optional: Nachts bauen, tags planen. Oder durchgehend. Der Rhythmus ist eine Einstellung.

Wer macht was

Rollen mit klaren Grenzen

Jede Rolle hat ein „macht nie“. Daraus entsteht der Gegendruck, der Qualität erzeugt: Niemand nimmt seine eigene Arbeit ab.

Mensch

Ziele, Prioritäten, Tests mit echten Daten auf dem Preview, Entscheidungen auf Stufe 3 und alles, was echte externe Systeme oder echte Daten berührt.

Front-Agent

Einzige Ansprechstelle. Wünsche und Befunde werden Tickets und Specs, Entscheidungen werden als eine Frage mit Optionen gestellt, der Stand kommt als Tabelle.

Macht nie: Worker steuern.

Controller

Startet und taktet Worker, Tests, Reviews und Waves. Erkennt Hänger, räumt auf, schreibt nach jedem Zyklus den Status. Läuft auf dem eigenen Rechner oder einem Server.

Macht nie: mit dem Menschen sprechen, Stufe 3 entscheiden.

Developer

Baut genau einen Auftrag testgetrieben auf eigenem Branch, mit Checkliste und Selbst-Review gegen die Spec.

Macht nie: nach main pushen, Tests abschwächen.

Tester

Prüft unabhängig mit frischem Kontext, lässt die vollen Testläufe selbst laufen, schreibt Befund und Urteil.

Macht nie: Code ändern.

Architekt

Prüft Specs vor dem Bau und grob die Grenzen danach. Stufe 3 geht als ADR mit Optionen an den Menschen.

Macht nie: Stufe 3 entscheiden.

Auditor und Retro

Prüfen die Fabrik, nicht das Produkt: Wo geht Zeit verloren, was häuft sich, was hat gewirkt? Jede Empfehlung mit Messwert.

Macht nie: etwas ändern.

Codex, Claude Code, Pi

Worker können jede dieser CLIs sein. Specs, Regeln und Antwortformat sind gleich. Modelle nach Komplexität, mit Eskalationsleiter und Kontingent-Fallback.

Neue Funktionen

Von außen nach innen

Gebaut wird erst, wenn Oberfläche, Daten und Logik abgestimmt sind. Fast jeder Fehler aus Live-Tests war ein Missverständnis über Daten oder Logik. Keiner davon hätte Code gebraucht, um aufzufallen.

Oberfläche

Entwürfe im Design-Werkzeug, dann ein Frontend-Fake: durchklickbar, erfundene Daten, ein paar Dummy-Aktionen, keine Logik. Der Export landet im Repo, damit Worker ihn ohne Design-Werkzeug lesen.

Freigabe: So sieht es aus und so bedient es sich.

Schnittstellen

Welche Daten rein- und rausgehen, sichtbar gemacht am Fake: Quellen, Felder, Zustände wie leer, mehrdeutig, Fehler.

Freigabe: Diese Daten fließen hier.

Logik

Der Ablauf in Worten und als Diagramm, eine Frage nach der anderen. Große Vorhaben als Karte von Entscheidungstickets über mehrere Sitzungen.

Freigabe: So denkt und handelt das System.

Bauen

Spec, Tickets, dann Architekt, Developer, Tester, Wave. Abnahme auf dem Preview gegen den Fake.

Abnahme durch den Menschen.

Gegendruck statt Vertrauen

Erst muss es funktionieren

Ein Review scheitert nur an echten Funktionsfehlern: Ein Ablauf aus der Spec läuft nicht, Daten gehen verloren, oder eine Änderung würde ein echtes externes System erreichen. Alles andere wird Schuld mit Kategorie und blockiert nichts.

Tests, Randfälle, Sicherheit, Last, Stilwerden gesammelt und in einer Härtungsphase abgearbeitet, sobald funktional eine gewisse Breite da ist.
Nach zwei Runden wird integriertwenn die Funktion läuft. Offene Punkte werden Schuld plus Abnahme auf dem Preview.
Git erzwingt das ReviewEin Push nach main ohne bestandenes unabhängiges Review wird vom Hook abgelehnt. --no-verify ist verboten.
TeststufenDeveloper prüfen gezielt. Tester und Waves prüfen voll. Docker nur beim Release.

Messen, dann entscheiden

Kapazität und Modelle werden erprobt, nicht geraten

Ob ein Worker startet, entscheidet die gemessene Last: CPU-, Speicher- und I/O-Wartezeit, freier Speicher, Gate-Warteschlange, fremde Last, Kontingente. Die Obergrenzen pro Host sind Startwerte. Sie steigen schrittweise, solange es ruhig bleibt, und sinken bei Druck. Dasselbe gilt für die Modellstufen pro Rolle: Bestehensquote und Runden aus dem Journal entscheiden, ob eine Rolle günstiger oder stärker fährt.

Hosts

Null bis viele Server. Alles lokal, ein Server, mehrere Server. Jeder mit eigener Kapazität, eigenem Orca-Environment, eigenen Pfaden.

Gates

Volle Testläufe laufen in fairen Plätzen, getrennt nach Unit- und Browser-Tests. Niemand überholt. Die Plätze passen sich der Last an.

Eskalationsleiter

Zweimal gescheitert, ein Modell höher. Kontingent knapp, Ersatz-Agent mit gleicher Leiter.

Reihenfolge bei Engpass

Kritischer Pfad, fast fertige Aufgaben, Waves, neue Entwicklung, Schuldenabbau.

Die Fabrik verbessert sich

Journal, Audit, Retro, Schnellspur

Journal

Jedes Ereignis mit Ursache als eine Zeile: Start, Ergebnis, Review-Runde, Wiederholung, Hänger, Wave, Gate-Wartezeit.

Pipeline-Auditor

Jede Nacht und bei Häufungen: die drei wichtigsten Verbesserungen und Risiken, jeweils mit Messwert, Ursache, Vorschlag und Erfolgskriterium.

Retro pro Lauf

Nach schwierigen Agentenläufen: ein bis drei belegte Änderungen an der Umgebung. Mechanische Fehler werden Checks, Ermessensfragen werden Reviewer-Regeln.

Schnellspur

Kleine Verbesserungen setzt der Controller selbst um, eine auf einmal. Die nächste Auswertung prüft, ob sie gewirkt hat.

Beispiel aus dem ersten Audit: Der Server war in 88 von 188 Minuten überlastet, Spitze Last 46,7 auf 12 Threads. Daraus wurde die Kapazitätssteuerung nach Messung.

Loslegen

In zehn Minuten eingerichtet

Ein Befehl im Projekt-Repo führt durch das Onboarding: Rhythmus, Tickets, Runner, Agent und Modelle, Hosts, Kapazität, Befehle, Preview, Review-Regeln, Design-Werkzeug, feste Regeln. Danach liegen Handbücher, Hooks, Skills und die Bundles für Controller und Front-Agent im Repo.

cd your-project
npx agentic-factory init      # Onboarding, eine Frage nach der anderen
npx agentic-factory doctor    # prüft Hooks, Werkzeuge, Hosts, Status
npx agentic-factory update    # holt Verbesserungen der Fabrik nach
