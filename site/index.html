DevOps-Harness für Software, die Agenten bauen

Ein Mensch.Ein Gesprächspartner.Eine Fabrik, die nachts weiterbaut.

Agentic Factory ist die Arbeitsweise und das Werkzeug, mit dem ein Mensch viele KI-Agenten Software bauen lässt, ohne den Überblick zu verlieren: ein Front-Agent, der zuhört, ein Controller, der unbeaufsichtigt steuert, unabhängige Prüfer, gemessene Kapazität und eine Pipeline, die sich selbst verbessert.

Auf einen Blick

Wie es funktioniert

Der Mensch spricht mit genau einem Agenten. Alles andere passiert dahinter: auf dem eigenen Rechner, auf einem oder mehreren Servern, oder beides.

1Ansprechpartner für den Menschen
0Pushes nach main ohne bestandenes Review. Die Git-Hooks lehnen sie ab.
2Review-Runden (Standard, einstellbar), dann entscheidet eine letzte Funktionsprüfung: Läuft die Funktion, wird integriert, der Rest wird Schuld mit Kategorie.
24/7optional: Nachts bauen, tags planen. Oder durchgehend. Der Rhythmus ist eine Einstellung.

Wer macht was

Rollen mit klaren Grenzen

Jede Rolle hat ein „macht nie“. Daraus entsteht der Gegendruck, der Qualität erzeugt: Niemand nimmt seine eigene Arbeit ab.

Mensch

Ziele, Prioritäten, Abnahme auf dem Preview in der eigenen Umgebung (automatisierte Tests nutzen nie echte Daten), Entscheidungen auf Stufe 3 (neue Verträge, Zuständigkeiten, Datenflüsse oder Technik) und alles, was echte externe Systeme oder echte Daten berührt.

Front-Agent

Einzige Ansprechstelle. Wünsche und Befunde werden Tickets und Specs, Entscheidungen werden als eine Frage mit Optionen gestellt, der Stand kommt als Tabelle. Ein Agent in einem Orca-Terminal oder ein Orca-Bot, den Orca weckt, wenn der Controller etwas zu melden hat.

Macht nie: Worker steuern. Produktcode schreibt er nur in der Design-Spur, wenn der Mensch sie verlangt (der Bot lässt dafür einen Worker laufen).

Controller

Startet und taktet Worker, Tests, Reviews und Waves. Erkennt Hänger, räumt fertige Worker auf, schreibt nach jedem Zyklus den Status. Ein Heartbeat weckt ihn von außen, sobald es etwas zu tun gibt, und meldet dem Front-Agenten, wenn er hängt (ein automatischer Neustart ist möglich, aber standardmäßig aus). Ist sein Kontext zu voll, startet er sich frisch. Läuft auf dem eigenen Rechner oder einem Server.

Macht nie: mit dem Menschen sprechen, Stufe 3 entscheiden.

Developer

Baut genau einen Auftrag testgetrieben auf eigenem Branch, mit Checkliste und Selbst-Review gegen die Spec.

Macht nie: nach main pushen, Tests abschwächen.

Tester

Prüft unabhängig mit frischem Kontext, lässt die vollen Testläufe selbst laufen, schreibt Befund und Urteil.

Macht nie: Code ändern.

Architekt

Prüft Specs vor dem Bau und grob die Grenzen danach. Stufe 3 geht als ADR mit Optionen an den Menschen. Auf Wunsch legt er eine ARCHITECTURE.md an und prüft sie nach jeder Wave.

Macht nie: Stufe 3 entscheiden.

Auditor und Retro

Prüfen die Fabrik, nicht das Produkt: Wo geht Zeit verloren, was häuft sich, was hat gewirkt? Jede Empfehlung mit Messwert.

Macht nie: etwas ändern.

Codex, Claude Code, Pi

Worker können jede dieser CLIs sein. Specs, Regeln und Antwortformat sind gleich. Modelle nach Komplexität, mit Eskalationsleiter und Kontingent-Fallback. Pi-Worker lassen sich je Rolle auf ein Modell festlegen (agents.piRoleModels).

Neue Funktionen

Von außen nach innen

Gebaut wird erst, wenn Oberfläche, Daten und Logik abgestimmt sind. Fast jeder Fehler aus Live-Tests war ein Missverständnis über Daten oder Logik. Keiner davon hätte Code gebraucht, um aufzufallen.

Oberfläche

Entwürfe im Design-Werkzeug, dann ein Frontend-Fake: durchklickbar, erfundene Daten, ein paar Dummy-Aktionen, keine Logik. Der Export landet im Repo, damit Worker ihn ohne Design-Werkzeug lesen.

Freigabe: So sieht es aus und so bedient es sich.

Schnittstellen

Welche Daten rein- und rausgehen, sichtbar gemacht am Fake: Quellen, Felder, Zustände wie leer, mehrdeutig, Fehler.

Freigabe: Diese Daten fließen hier.

Logik

Der Ablauf in Worten und als Diagramm, eine Frage nach der anderen. Große Vorhaben als Karte von Entscheidungstickets über mehrere Sitzungen.

Freigabe: So denkt und handelt das System.

Bauen

Spec, Tickets, jedes Ticket vom Front-Agenten geschärft, dann Architekt, Developer, Tester, Wave. Abnahme auf dem Preview gegen den Fake.

Abnahme durch den Menschen.

Gegendruck statt Vertrauen

Erst muss es funktionieren

Ein Review scheitert nur an echten Funktionsfehlern oder einem Architekturverstoß: Ein Ablauf aus der Spec läuft nicht, Daten gehen verloren, oder eine Änderung würde ein echtes externes System erreichen. Alles andere wird Schuld mit Kategorie und blockiert nichts.

Immer dabei: Code-Qualität und Architekturwerden in jedem Review geprüft. Ein Architekturverstoß blockiert, Qualitätsbefunde werden behoben oder Schuld.
Nicht im Alltag: Last und SicherheitSie bremsen die Entwicklung, darum laufen sie in der Härtungsphase und vor jedem Release, zwingend: keine Freigabe, solange eine dieser Schulden offen ist.
Nach der eingestellten Zahl von Runden wird integriert(standardmäßig zwei), wenn die Funktion läuft. Offene Punkte werden Schuld plus Abnahme auf dem Preview.
Git erzwingt das ReviewEin Push nach main ohne bestandenes unabhängiges Review wird vom Hook abgelehnt. --no-verify ist verboten. Die Hooks laufen lokal und fangen ehrliche Fehler ab, sie sind keine Sicherheitsgrenze: Schütze main zusätzlich auf dem Server.
Die Welle merged genau das GeprüfteFür Code läuft der volle Gate-Lauf in der Welle selbst, kein früheres Ergebnis zählt. Der Controller hält den geprüften Commit fest (reviewed.mjs). Ist ein Branch nach seinem Review weitergewandert, stoppt die Welle.
Nur Doku: optional ohne Tester-RundeMit docsOnly.enabled (standardmäßig aus) überspringt ein Ticket, das sich als reine Dokumentation erklärt und nur Dokumentation ändert, seine Tester-Runde. Das Gate spart es nicht.
TeststufenDeveloper prüfen gezielt. Tester und Waves prüfen voll. Docker, Sicherheit und Last beim Release, als Bedingung der Freigabe.
# <task> review, round 1

Messen, dann entscheiden

Kapazität und Modelle werden erprobt, nicht geraten

Ob ein Worker startet, entscheidet die gemessene Last: CPU-, Speicher- und I/O-Wartezeit, freier Speicher, Gate-Warteschlange, fremde Last, Kontingente. Die Obergrenzen pro Host sind Startwerte. Sie steigen schrittweise, solange es ruhig bleibt, und sinken bei Druck. Dasselbe gilt für die Modellstufen pro Rolle: Bestehensquote und Runden aus dem Journal entscheiden, ob eine Rolle günstiger oder stärker fährt.

Hosts

Null bis viele Server. Alles lokal, ein Server, mehrere Server. Jeder mit eigener Kapazität, eigenem Orca-Environment, eigenen Pfaden.

Gates

Volle Testläufe laufen in fairen Plätzen, getrennt nach Unit- und Browser-Tests. Niemand überholt. Die Plätze passen sich der Last an. Jedes Projekt hat sein eigenes Gate; die Wave lässt für Code immer den vollen Lauf selbst laufen.

Eskalationsleiter

Zweimal gescheitert, ein Modell höher. Kontingent knapp, Ersatz-Agent mit gleicher Leiter.

Reihenfolge bei Engpass

Kritischer Pfad, fast fertige Aufgaben, Waves, neue Entwicklung, Schuldenabbau.

Die Fabrik verbessert sich

Journal, Audit, Retro, Schnellspur

Journal

Jedes Ereignis mit Ursache als eine Zeile: Start, Ergebnis, Review-Runde, Wiederholung, Hänger, Wave, Gate-Wartezeit.

Pipeline-Auditor

Jede Nacht und bei Häufungen: die drei wichtigsten Verbesserungen und Risiken, jeweils mit Messwert, Ursache, Vorschlag und Erfolgskriterium.

Retro pro Lauf

Nach schwierigen Agentenläufen: ein bis drei belegte Änderungen an der Umgebung. Mechanische Fehler werden Checks, Ermessensfragen werden Reviewer-Regeln.

Schnellspur

Kleine Verbesserungen setzt der Controller selbst um, eine auf einmal. Die nächste Auswertung prüft, ob sie gewirkt hat.

Beispiel aus dem ersten Audit: Der Server war in 88 von 188 Minuten überlastet, Spitze Last 46,7 auf 12 Threads. Daraus wurde die Kapazitätssteuerung nach Messung.

Ohne dass jemand zusieht

Läuft allein und sagt, wann es nicht mehr läuft

Ein Controller, der nachts arbeitet, braucht jemanden, der ihn weckt, aufräumt und merkt, wenn er stehen bleibt. Das sind keine Zusätze des Controllers, sondern Teile der Fabrik außerhalb von ihm.

Front-Agent: Terminal oder Bot

Standard ist eine Agenten-Sitzung in einem Orca-Terminal. Alternativ ein Orca-Bot mit eigenem Chat und Gedächtnis: Orca prüft alle 5 Minuten den Status und weckt ihn nur bei Neuigkeiten, ein ruhiges Projekt kostet keine Modellzeit. Den Bot legst du vorher selbst in Orca an. Er schreibt keinen Produktcode.

Heartbeat

Ein Job auf dem Rechner des Controllers (launchd auf macOS, sonst cron, jede Minute) weckt ihn bei einer neuen Worker-Nachricht, einer fertigen Welle oder einer neuen Zeile in inbox.md, ein Projekt ohne Neuigkeiten höchstens alle 30 Minuten. Lässt er sich nicht einplanen, schlägt start fehl und sagt, warum.

Hänger

Ist der Controller beschäftigt, sein Terminal verändert sich noch, aber Status und Journal sind 25 Minuten unverändert (hosts.controller.hung.minutes), erfährt es der Front-Agent. Ein ruhiger, nur als beschäftigt gelesener Controller wird dadurch nicht erfasst. Der automatische Neustart bleibt aus, bis hosts.controller.hung.restart auf true steht, und gilt nur einmal, ein zweiter Hänger wird gemeldet. Nach einer Welle oder im Leerlauf startet sich der Controller bei über 50 % Kontext von selbst frisch; das beendet seine laufende Sitzung, und dass die Worker das überstehen, ist nicht belegt.

Aufräumen

Ein Worker gilt als fertig nach seinem Dispatch-Status in Orca, auch wenn sein Agent noch am Prompt sitzt. Entfernt wird er nur, wenn sein Worktree sauber und sein Branch gemergt oder gepusht ist. node cleanup.mjs löscht nichts ohne --apply, sondern listet nur auf. node keep.mjs <key> behält einen Worker.

Mehrere Projekte, ein Rechner

Mehrere Fabriken auf einem Rechner sind vorgesehen: Jedes Projekt hat ein eigenes Controller-Verzeichnis mit eigenem Gate (init schlägt ~/controller-<projekt> vor, wenn ~/controller schon einem anderen Projekt gehört). Das ist bisher nur gegen Attrappen getestet. Bekannte Grenzen: Der Controller liest das gemeinsame Orca-Postfach und sieht die Betreffzeilen anderer Projekte, und die Wave-Logs liegen unter festen Namen in /tmp, zwei Controller auf einem Host überschreiben sie (F17).

Was belegt ist und was nicht

Was wirklich gelaufen ist

Die Fabrik ist ein Anfang, kein Endzustand. Hier steht, was in einem echten Lauf war, was nur gegen Attrappen getestet wurde und was offen ist. Stand: Release v0.1.13.

Echt gelaufen

Dreimal Ende zu Ende auf macOS in Wegwerf-Projekten, mit einem Claude-Code-Controller und einem Orca-Bot als Front-Agent. Der letzte Lauf lief auf dem Stand von v0.1.13 ohne dessen letzte kleine Korrektur (#70). Es kamen vier Tickets nach main, zwei davon über den Dokumentationspfad. Jede Welle ließ das volle Gate für Code laufen, eine Welle stoppte, weil nach dem Review noch ein Commit gepusht wurde, und das Aufräumen entfernte die fertigen Worker mit --apply.

Nicht echt gelaufen

Ein Controller auf einem anderen Rechner, ein Controller mit einer anderen Agenten-CLI als Claude Code, eine Dokumentations-Welle auf einem entfernten Worker-Host, der automatische Neustart eines hängenden Controllers (aus, solange du ihn nicht einschaltest) und überhaupt ein Neustart des Controllers, auch der bei hoher Kontextauslastung: Dass die Worker das Schließen seines Terminals überleben, ist nicht belegt.

Nur gegen Attrappen

Die Tests ersetzen Orca, ssh, launchctl, crontab und gh durch Attrappen, die ihre Aufrufe aufzeichnen. So sind Heartbeat, Wecken, Aufräumen, Kapazität, die Bot-Überwachung und die Regeln für eine zweite Fabrik geprüft. Der Formatierer für gestagte Dateien lief nur mit einem Ersatz, nicht mit prettier.

Offen

Orca hat einen Claude-Code-Controller, dessen wait.mjs im Hintergrund lief, in einem Lauf als beschäftigt gelesen und in einem anderen nicht. Dass wait.mjs der Grund ist, ist wahrscheinlich, nicht bewiesen. Im letzten echten Lauf musste er einmal von Hand geweckt werden, nach 12 Minuten. Die Ursache ist nicht verstanden. Wer unbeaufsichtigt arbeitet, sollte darauf achten.

Seit v0.1.13 auf main, noch nicht veröffentlicht

Dies steht in keinem Release und ist in keinem echten Lauf bestätigt; die Tests laufen gegen Attrappen.

Das Ticket schärfen, bevor es fertig istDer Front-Agent bewertet jedes Ticket (auch eins aus einem fremden Tracker, das er erst in die Ticketform bringt) gegen Spezifikation, Code und Glossar, schließt, was der Kontext beantwortet, und fragt nur die echten Lücken. Das Ergebnis steht im Ticket (Assessed:, Annahmen, Fragen, Quellen); ein Ticket mit offener blockierender Frage ist needs-info. Der Controller prüft per Code nur die Form (steering.readyCheck: in bestehenden Projekten zuerst warn), nicht die Qualität. Ein Fall ändert sich nach dem Update auch mit warn: Im GitHub-Issue-Modus wird ein Issue mit needs-info, auch zusammen mit dem Ready-Label, nicht mehr gelistet oder übernommen (ein schon in Arbeit befindliches wird nicht angehalten); das Label nach der Antwort entfernen.
Worker fragen den Controller, nie den MenschenDie Spec sagt es, und ein Worker, der auf die Antwort eines Menschen wartet, wird erkannt und dem Controller gemeldet, wo Orca es meldet.
Der Controller sagt dem Heartbeat, wann er fertig istDamit wird auch ein Controller geweckt, den Orca als beschäftigt liest. Das ist die Antwort auf das offene Problem oben und noch durch keinen echten Lauf bestätigt.
Neustart ohne Orca-Option --keep-openrestart.mjs läuft auch auf Orca-Versionen ohne sie (dass das neue Terminal überlebt, wurde einmal auf einer Orca-Version beobachtet, nicht aus einer Option abgeleitet) und meldet, wenn danach zwei oder gar kein Controller läuft.

Loslegen

So fängst du an

Voraussetzungen: macOS oder Linux (Windows: WSL 2), Orca (der Runner) läuft, eine angemeldete Agenten-CLI (Claude Code, Codex oder Pi), Node 22 oder neuer und git mit Name und E-Mail. Danach führt dich der Front-Agent in Orca durch das Onboarding, fragt unter anderem, ob du mit ihm im Terminal oder mit einem Orca-Bot sprichst und wo die Dateien des Controllers liegen, richtet Handbücher, Hooks und Skills ein und startet die Fabrik.

Der kurze Weg: ein Prompt. Öffne dein Projekt in einem beliebigen Agenten (wenn möglich in Orca) und gib ihm diesen Satz. Er prüft die Voraussetzungen, nennt, was fehlt, und zieht bei Bedarf selbst in ein Orca-Terminal um.

Set up the agentic factory for this project. If ~/agentic-factory does not exist, clone https://github.com/bussard76/agentic-factory.git into it; otherwise update it with git -C ~/agentic-factory pull --ff-only. Then read ~/agentic-factory/START.md and follow it: check the prerequisites, move into Orca if needed, and guide me through the onboarding.

Dasselbe von Hand. Kopiere die Befehle in ein Terminal:

# 1. Die Fabrik holen (gibt es sie schon: git -C ~/agentic-factory pull --ff-only)
git clone https://github.com/bussard76/agentic-factory.git ~/agentic-factory

# 2. Ins Projekt wechseln (neues Projekt: mkdir my-app && cd my-app && git init -b main && git commit --allow-empty -m "Initial commit")
cd ~/pfad/zu/deinem-projekt

# 3. Projekt in Orca registrieren und den Front-Agenten in einem Orca-Terminal starten
ORCA="${ORCA_CLI_COMMAND:-orca}"   # Linux außerhalb von Orcas Terminals: ORCA=orca-ide
$ORCA repo add --path "$PWD"
$ORCA agent launch --agent claude --worktree "path:$PWD" --surface terminal --focus \
  --prompt "Read ~/agentic-factory/START.md and set up this project."

Statt claude geht codex oder pi. Windows: WSL 2 installieren (wsl --install -d Ubuntu in einer Admin-PowerShell), Orcas Terminal auf WSL laufen lassen, Node, git und die Agenten-CLI in WSL installieren, das Projekt unter ~/ ablegen; die Befehle bleiben gleich.

Für ein bestehendes Projekt gibt es einen eigenen Prompt in der README. Bekannte Grenzen stehen in den Release-Notes (Known limits) und in debt.md. Zwei triffst du früh: Für die erste Welle legt nichts das Integrations-Worktree an (im letzten Lauf tat es der Controller selbst, #28), und beim ersten Start fragt Claude Code einmal, ob es dem Ordner des Controllers vertraut; das beantwortet start nicht für dich (#23). Mit der Fabrik leben

So viel Standard wie möglich, so viel Eigenes wie nötig

Jedes Projekt passt seine Kopie an, und die Fabrik entwickelt sich weiter. Beides geht zusammen, weil ein Update nichts überschreibt, was das Projekt geändert hat.

Aktualisieren

Das Update überschreibt nur unveränderte Dateien. Geänderte bleiben, ihre neue Fassung landet in .factory/new/ zum Zusammenführen, danach folgt start. Ein geänderter Controller-Leitfaden CONTROLLER.md zuerst: Bis er zusammengeführt ist, stoppt jede Welle (WAVE-NOT-STARTED), nichts wird aufgeräumt, und jede Inbox-Zeile weckt den Controller. update, start und doctor warnen davor. Den Prompt dafür enthält die README.

Was auf deinem Rechner landet

Außerhalb des Projekts schreibt start die Skills, ~/front-agent/<projekt>/, das Controller-Verzeichnis mit dem Gate des Projekts, ~/load.log, den Heartbeat und die Statusüberwachung. Die Liste samt Entfernen steht in Getting started.

Zurückgeben

Was sich im Projekt bewährt und anderen hilft, kommt als Pull Request zurück. Jede Änderung wird einzeln geprüft: in den Standard, als Mechanismus mit dem Wert im Projekt, oder sie bleibt im Projekt.

Vorschau: Standard außerhalb der Historie

Mit init --untracked-standard checkt ein Projekt nur noch ein, was ihm gehört. Wer den Code anders bearbeitet, trägt den Stack nicht mit. Das lief noch in keinem echten Projekt. Details
